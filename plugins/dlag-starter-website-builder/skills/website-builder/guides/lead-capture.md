# Lead capture stays in the Worker

Use a same-origin React Router action on the Cloudflare Worker. Keep Supabase persistence, durable delivery-intent creation and Resend preparation server-side. No Supabase Edge Function or browser email SDK is added. Form labels, help text, required state, pending state, error summary and confirmation are part of the feature. Associate field errors with aria-describedby; preserve valid entered values on a rejected submission and announce the resulting state. Minimize collected personal data and link the owner's privacy notice.

Validate method, expected origin, content type, byte limit, schema, selected abuse control and idempotency before persistence. A finite Content-Length header is useful early rejection but is not a trustworthy size limit; count streamed bytes and stop before formData parsing. Use an application-owned bounded form parser or a reviewed existing helper. Restrict fields, reject duplicate form fields and unexpected keys, enforce maximum lengths and validate email on the server. Browser validation is helpful UX and never replaces the server boundary. The [action recipe](../templates/lead-action.md) defines these integration contracts.

For same-origin browser submissions require an exact Origin equal to the configured public site origin; if other clients need absent Origin, define a separate authenticated path. Use CSRF protection appropriate to session-bearing forms. Apply a server-enforced abuse/rate policy before accepting public submissions. If the project has explicitly selected Turnstile, verify its token server-side and enforce expected hostname/action; token presence alone is insufficient. Missing selected controls fail closed. Do not introduce Turnstile or another provider silently.

Create a stable submission ID bound to the validated payload and purpose. Atomically persist a unique receipt and a notification intent, returning the existing receipt for a retry of the same payload; a key reused with different content is a conflict. The database operation must enforce concurrency uniqueness. This is an application contract requiring real Supabase SQL/RLS integration; an in-memory mock proves only the mock behavior. Do not send email before the lead is durable.

Return validation errors without a persistence/send call. Distinguish saved receipt, pending notification, provider accepted, provider delivered and unknown after timeout. A saved lead may return 202 with notification pending; the UI must say 'Your request was saved. Email confirmation is pending.' It must not say 'Email sent.' A failed persistence returns a retryable error without claiming a receipt. A failed notification after saving must not hide or duplicate the receipt.

Use `dlag-starter-core:resend-transactional` to prepare a fixed server-owned transactional template and recipient, durable outbox state and provider idempotency. Never accept arbitrary recipient, sender, subject or HTML from the public form. The business notification may go to an approved internal mailbox; do not turn lead capture into bulk marketing. A separate subscriber newsletter provider is unselected. For a simple requested notification, use a bounded synchronous attempt after the durable save, following the Core transactional-email Playbook for atomic claiming, result persistence and recovery. The lead remains saved if delivery fails. A separate queue or schedule is needed only if the requested delivery guarantees require it; none is selected by default. The action recipe initially returns notification pending. If implementing an inline attempt, update that result to the observed accepted, failed or unknown state without claiming delivery. A durable intent table alone does not execute email.
