# 01. Run a security review

> Role boundary: review supplied local evidence with Read/Grep/Glob/Skill and return findings in chat. Execution, remediation, configuration, external requests and saves require a separate authorized caller. Examples below do not grant those tools or permissions.

## First gate and evidence continuity

Security Review runs before Quality Review and the orchestrator's repository-health review. Pin the candidate, including dirty/untracked files. A branch name or commit SHA does not identify additional working bytes. Record the observed date, exact paths and available artifact hashes; unknown identity stays unknown. Existing reports apply only to the candidate and scope they actually inspected. If Quality already ran and security changes follow, its implementation conclusions need renewed review of the changed candidate.

1. Scope the review and its immediate neighbors. Read every changed protected route plus its identity verifier, permission helper, database policies, serialization and storage access paths. Review a complete user operation through its denial and failure branches rather than isolated lines. Record missing provider, schema, build and runtime evidence as reduced coverage. The Starter stack is React/Vite with React Router framework SSR on Workers; Supabase database/Auth; Cloudflare secrets; R2; transactional Resend; optional hosted Stripe. It supplies no CMS dashboard or selected job/newsletter service.
2. Work through the [deterministic search reference](../references/grep-patterns.md). The Specialist performs only searches available in its actual read tools. Shell/scanner commands remain proposed to an authorized caller. Use file names and redacted evidence for possible secrets; never print credential values into a report or conversation. A search hit is a lead, not a finding; no hits do not prove safety.
3. Walk the [surface checklist](../references/audit-checklist.md) in order: framework boundaries, identity/tenant policy, secrets/SQL, webhook intake, dependencies, headers/abuse control, generated-code failure patterns, logs/PII. Mark each inspected surface, its evidence and unavailable parts. A silent skipped category must not read as a pass.
4. Triage before proposing a fix. Use the [severity rubric](../references/severity-rubric.md). A finding needs path:line or an exact supplied section, a redacted excerpt, actor/input, missing control, plausible path to harm, impact and confidence. Distinguish a confirmed vulnerability from a hypothesis or an unreviewed surface. Never lower payment or PII exposure severity to hurry the gate.
5. Propose the smallest correction using [remediation patterns](09-remediation-playbooks.md) and the [code contracts](../references/secure-by-default-snippets.md). The implementation owner applies authorized changes. Do not opportunistically refactor, rewrite history or rotate credentials from this read-only role. A proposed fix is not remediation evidence. Record the owner, affected paths, expected allowed/denied behavior and proof still needed.
6. After relevant corrections, review the actual updated candidate and all affected neighboring invariants. An old green check can carry forward only when the relevant inputs and behavior are unchanged. Repeat the full applicable security pass for Medium-or-higher remediation, including effects beyond the changed line. All unresolved Medium-or-higher findings block progression to Quality Review; a narrative report is not a waiver.
7. Return a complete [report](../references/audit-output-format.md) even with no findings. A cleared scoped review means no confirmed unresolved security finding in inspected scope, never that every application surface is safe. The authorized caller may save the report at an existing project location per [report destination rules](10-report-format.md).

## Design mode before code

Use [threat modeling](11-threat-model-before-features.md), [response boundaries](12-response-and-tenant-boundaries.md), [webhook trust](13-webhook-forgery-replay-and-recovery.md), [exposure scope](14-browser-log-and-context-secrets.md) and [risk verification](15-verify-actual-risk.md). These prepare a packet from actual supplied facts. They do not grant execution authority, select new providers or create an accepted architecture. The author cannot independently approve their own new packet. Synthetic cases demonstrate review reasoning only.

## Stop and escalation rules

If the implementation is outside the inspected stack, state REDUCED COVERAGE and the missing specialist/evidence. If a verifier, policy or helper is unavailable, stop the dependent conclusion rather than invent its behavior. If evidence contains a live credential, record only class/location, preserve existing evidence safely and alert the authorized custodian. Never read more secrets to prove a suspected exposure. Commit, push, provider operations and publication need their own explicit task authorization after all review gates.
