# TypeScript and HTTP Foundation procedure

1. Read the existing package scripts, lockfile, React Router configuration, TypeScript configuration and Worker bindings. Classify this as React Router framework SSR on Cloudflare Workers. Preserve its selected package manager and installed major versions. Do not apply SvelteKit route types, Vercel Node rules, Node-only libraries or a library-publishing tsconfig to this app.
2. Keep strict TypeScript and bundler-compatible ESM. Import route argument/component types from React Router's generated `./+types/<route>` when available. Use type-only imports for types. Keep provider credentials and Node-incompatible code outside browser modules; use `.server.ts` modules for server boundaries. Serialize only approved display data from loaders.
3. Validate every form, JSON body, route ID, query and external response at entry. Treat parsed values as unknown until narrowed. Check content type, byte/field/count limits and reject unsupported methods early. Reuse the installed validation library; do not add one just to parse a tiny form. The [bounded form recipe](../examples/request-validation.mjs) illustrates limits, not a complete framework adapter.
4. Use loader GETs for reads; use actions or resource routes for mutations. Verify session, origin/CSRF protection and record ownership on each mutation. Derive owner from the verified session. Use `dlag-starter-core:identity` and `dlag-starter-core:data-foundation` for session/RLS details.
5. Match status and headers to the accepted operation and caller. Distinguish malformed content, compatible validation policy, authentication challenges, permission refusal or existence concealment, unsupported methods/media types, failed supplied preconditions, resource conflicts and safe unexpected failures. Use [the full HTTP procedure](../http/playbook.md) and [status decision worksheet](../http/templates/status-code-matrix.md), including POST creation SHOULD versus new PUT target MUST rules, 400/422 compatibility, 401 challenge, 405 Allow, 412 preconditions and HEAD/204/304 no-content behavior. Browser login redirects may be appropriate for a protected page; constrain return destinations. Private responses need a reviewed private/no-store cache policy and must not share users through an edge cache.
6. Await required writes, bound concurrency, handle known errors narrowly and return a readable action state. Do not swallow errors or expose raw exceptions. Store provider delivery status separately from the main mutation, and avoid promising background completion without a durable selected runner.
7. Save the [boundary contract](../templates/boundary-contract.md), read edits back and run only affected existing scripts when tools and user authorization allow. This role grants file authoring, not shell execution: provide exact existing script names for the operator when needed. Do not run arbitrary curl/download scripts, change shell dotfiles, install packages or claim tests ran without output. Use `dlag-starter-core:ready-check`.
