# Design and draft the requested data change

1. Preserve the user's request, accepted decisions and file ownership. Identify the user action, entities, relationships, key queries, personal or tenant ownership, expected volume, retention/deletion and sensitivity. Ask only for missing decisions that change the design. Keep measured values, forecasts and unknowns distinct.
2. Read the existing schema, applied migrations, query call sites, package/lockfile and supplied version/environment facts. Record actual server and client versions, migration runner boundaries and source revision. Do not read credentials or connect to discover missing facts. Supabase Postgres/Auth, Workers, Cloudflare secrets and R2 are selected services; keep those responsibilities explicit.
3. Follow [principles](00-principles.md), [schema](01-schema-design.md) and [indexing](02-indexing.md). Name each table's purpose and lifecycle. Choose columns, constraints, key relationships, query shapes, pagination and indexes together. Check tenant-bearing relationships rather than trusting a globally valid record ID. Record one recommendation and its workload rationale in the [schema specification](../templates/schema-spec.md).
4. For personal ownership, the [notes draft](../examples/owned-notes.sql) shows an indexed UUID owner, explicit grants, RLS and SELECT/INSERT/UPDATE/DELETE policies. UPDATE needs an existing-row test, a resulting-row WITH CHECK and a corresponding SELECT policy. Never retry an empty policy-filtered result with an admin key or grant anonymous writes to bypass a failure. RLS does not replace Worker authentication or input validation.
5. For existing data, read [migration patterns](03-migrations.md) and [live-schema changes](11-live-schema-migration.md). Prepare a [migration proposal](../templates/migration-plan.md) with exact objects, additive phases, each lock/scan/rewrite, source of truth for backfill, independently committed batches, compatibility, verification, rollback and recovery after writes. Keep historical unknown values unknown. Preserve applied migrations.
6. For performance, inspect the supplied plan and statistics with [plan review](review-query-plan.md). State whether the plan is estimated or actual, when it was captured, its data scale and what is missing. Do not execute EXPLAIN ANALYZE: it runs the query and requires a separately authorized environment. Do not assert a new index or pool setting improved anything without observation.
7. For tenant data, fill the [boundary worksheet](../templates/tenant-boundary-proof.md). Enumerate ordinary requests, joins, aggregate/mutation/export paths, privileged jobs if present, pooled context, R2 objects, caches and search. Security Review evaluates access design and negative cases before acceptance. A diagram or provider selection is not isolation proof.
8. Draft only requested local files and examples. Check model/query consistency, constraint names, index rationale, delete/retention paths, old/new writer compatibility and local references. No new service or ORM is selected implicitly.
9. Prepare meaningful checks using synthetic identities: owner succeeds; another identity cannot read or change data; no session fails; ownership transfer fails without changing stored state; invalid input causes no writes. Define expected HTTP and database effects separately. Native tests use ordinary principals and a separate privileged fixture/effect verifier in an authorized disposable environment.
10. Save the design, migration proposal when needed, and expected checks in the project's existing document location. Report actual source checks, executed evidence and missing native/provider proof. Security Review precedes Quality Review for implemented changes; the review does not itself authorize migration, deployment or publication.
