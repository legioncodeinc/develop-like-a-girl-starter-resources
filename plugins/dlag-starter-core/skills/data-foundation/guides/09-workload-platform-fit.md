# Normalize workload before a platform-fit decision

Use the [fit worksheet](../templates/platform-fit-decision.md). The selected stack is described in [selected services](08-serverless-platforms.md); no provider change is implied.

1. Read named schema, recent migrations, runtime/client/ORM files and supplied non-secret PostgreSQL/provider metadata. Capture actual versions and environment. Do not connect to a live database, expose a connection string or run EXPLAIN ANALYZE merely to fill a decision table. Ask only for missing material constraints.
2. Normalize tenant/account rows and growth, read/write rates, transaction contention, hot queries, concurrent client connections, serverless bursts, session/LISTEN needs, existing background work, extension requirements, object bytes/egress, realtime requirements if any, residency and latency targets. Separate measured, forecast and unknown inputs. Preserve units and periods. Do not infer throughput from user count.
3. Inventory services individually: Supabase identity/session, Data API/RLS and database; Workers backend/SSR; R2 objects; Cloudflare secrets and transactional Resend. State who owns each interface and its failure behavior. An optional realtime requirement does not select a provider or establish durable event delivery. Existing jobs need an owner, but this review does not select a queue or scheduler.
4. Match connection mode to the actual access path. HTTP Data API and a server SQL client's transport have different behavior. For SQL clients, verify session/prepared-statement/pipelining semantics, transaction support, network reachability, per-instance limits and migration/restore connection needs from current official documentation. Do not paste endpoint credentials or infer correctness from one port number.
5. Require actor/tenant authority at the actual API and data paths. API-exposed Supabase tables need their documented grants/RLS design and ordinary-user negative checks. A server-only access design needs explicit authority and privileged-role isolation. Database design, identity and Security Review are distinct responsibilities. Any private realtime/object path requires its own authorization and revocation checks.
6. When cost is in scope, use dated owner-supplied quantities and current official rates for the complete selected services: compute/storage, backups/PITR, replicas/branches, auth, object storage/egress, mail, networking and operator effort. Missing rates stay unknown. No universal cheapest-provider or free-idle claim is permitted.
7. Recommend one fit decision against must-have constraints, explain counterevidence and identify one bounded validation exercise. Missing version/region/extension/recovery facts can make it provisional. Complete [recovery and exit](10-recovery-and-exit-fit.md) before making a recovery claim. Do not provision, install, alter flags, migrate or switch services through advisory work.
