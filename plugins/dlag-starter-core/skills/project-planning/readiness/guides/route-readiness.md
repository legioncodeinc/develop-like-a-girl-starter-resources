# Hand off decisions using available Starter methods

1. Use the local [discovery method](../../discovery/playbook.md) for demand preparation/evidence, [strategy](../../strategy/playbook.md) for product decisions, [UX](../../design/playbook.md) for planned flows/states and [estimation](../../estimation/playbook.md) for conditional effort/time/cash. The owner already approved the Starter stack; do not reselect providers through a missing stack-selection specialist.
2. Give actual implementation owners only relevant facts and unresolved questions. Browser website work uses the separately installed Website Builder pack; app work uses the separately installed App Builder pack. Check their actual availability and task authority before dependent work. Native/mobile/host-plugin/CLI requirements need a separately designated owner and explicit scope decision; Starter does not invent those capabilities.
3. Use `dlag-starter-core:technical-explainer` for supplied-source explanations and `dlag-starter-core:project-notebook` for authorized project documents/requirements. Boundary contracts require actual owner-designated authors and accepted terms; no contract specialist is implied. Existing project ownership takes precedence over reinitializing a repository.
4. Security implementation questions use actual identity/data/secrets/dependency/platform owners as appropriate: `identity`, `data-foundation`, `secrets`, `dependency-review`, `cloudflare-platform` and `supabase-platform` in `dlag-starter-core`. Review uses `security-review`, then `quality-review`. An owner-designated operator owns actual response/recovery. No name in a table proves dispatch, staffing, acceptance or a running control.
5. Return one readiness recommendation, role map, slice, understanding state and concrete next handoff. Missing providers/accounts/assets/commercial reviewers stay gaps; do not create accounts, configure platforms, install tools, send, spend or build from this advisory.

Project Planning can use these methods directly only within its actual tools and requested documentation scope. A specialist dispatch requires actual availability and authorized delegation. Missing native delegation is not a reason to claim that a specialist ran.


Scope: this is readiness preparation in requested local Markdown. Accepted Starter providers remain fixed; a different product form can be a provisional qualification result, but requires a separate scope/owner decision for implementation. No source/example text authorizes a provider, account, installation, external send or app change.
