# Route a website build

Use the separate Website Builder plugin for an approved website brief and the selected React Router SSR stack. Core can prepare scope, dependencies and a concrete handoff if that plugin is unavailable. A source tree or namespaced command written in a document does not establish installation.

## Inputs

Obtain the user outcome, audience, conversion action, exact pages, approved copy and brand inputs, repository state, selected platform, required content changes, acceptance criteria and authorized local work. Record which runtime, browser, build and provider tools the caller actually has. Identify unknown content, permissions, services, integration contracts and external costs before dependent implementation.

Keep the application backend on Workers, customer identity and data on Supabase, secrets in Cloudflare, uploads in R2 and transactional messages in Resend. Content is owned in the repository. There is no selected CMS dashboard, editor identity provider, newsletter or job vendor. Optional hosted Stripe Checkout belongs to App Builder's payments capability. Do not add a database, auth, tracking, blog or webhook merely because a broad website procedure mentions one.

## Select phases deliberately

1. **Architecture and workspace.** Inspect the repository and approved scope. Choose a coherent React/Vite and React Router SSR layout, Workers target, package manager already in use and content location. Avoid creating a second application or CMS service without a scoped decision. Preserve existing changes and one owner per path.
2. **Performance and browser baseline.** Record rendering decisions, route boundaries, caching assumptions, responsive assets, font behavior and critical user flow. Browser Checks owns actual browser and performance observations when the capable caller can execute them. A build result does not prove field Core Web Vitals.
3. **Discoverability.** Website Builder prepares page titles, descriptions, canonical URLs, crawl/index rules, sitemap data, accessible semantics and justified structured data. Treat a noindex requirement as an intentional policy. Content and route metadata must use the same approved source. No separate SEO Specialist or search-ranking promise is implied.
4. **Telemetry decision.** Ask which observations are necessary to verify the outcome and what consent/data limits apply. No analytics vendor is selected by default. Exclude the phase if not approved; do not invent a tracking integration.
5. **Data boundary.** If persistence is required, Data Foundation defines schema, migration, ownership and query contracts; Supabase Platform qualifies access and environment assumptions. Require tenant denial evidence and recovery expectations. If no persistence is needed, document the exclusion instead of scaffolding tables.
6. **Customer identity.** Use Identity only when the site actually needs authenticated customer behavior. Specify session, recovery, authorization and server enforcement separately from login UI. Do not confuse content authors with customer accounts. Identity absence is valid for a public site.
7. **Repository content.** Define accepted content files and types, editorial ownership, schema validation, media provenance and update/rebuild behavior. Use repository content with the current website method. A CMS dashboard, external Collections API, editor SSO and live preview service require a future explicit capability decision.
8. **Conversion and lead flow.** Define required fields, validation, consent, spam resistance, success/failure states, duplicate behavior, destination and retention. The backend must enforce the contract. R2 handles approved files; Resend handles approved transactional confirmations. A local form preview is not proof of delivery or CRM synchronization.
9. **Blog or repeated content.** Include only if required. Website Builder owns the Markdown/MDX compiler, content map, rendering and sanitization choice. Require exact slug, metadata, empty/error, image and content-update behavior. A static one-page site may omit this phase with a reason.
10. **Integrations and callbacks.** First pin request, response, authentication, retry, idempotency and error contracts. Use App Integrations only when that separate plugin and its scoped method are available. Raw signatures and deduplication must be observed where applicable. No callback, message or provider write occurs from Build Lead.
11. **Conversion review.** Check the approved user path, copy, navigation, accessibility, mobile layout, error recovery and primary action. Report a hypothesis as a hypothesis; a visual review cannot prove conversion lift. Never submit a real lead or purchase without its specific authorization.
12. **Visual system.** Design Foundation establishes or applies product context and tokens. React shadcn components and UI Primitives preserve accessible behavior, focus, events, state and upstream/customization boundaries. React Foundation handles component architecture; Asset Delivery handles image/font delivery. Do not confuse a component spec with mounted browser proof.

For each selected phase record its owner, inputs, output paths, dependencies, checks, actual observations and gaps. Existing architecture or content may satisfy a phase; cite that evidence. Never convert a skipped phase into a passed implementation.

## Handoff and sequencing

Arm Website Builder with the approved brief, exact paths, selected phases and exclusions, content/brand sources, accepted boundary revisions, deadline and actual tool limitations. Design and data preparation may run in parallel only with independent leases and stable interfaces. Start dependent implementation after its required agreement is accepted. Keep each worker's scope and output distinguishable.

The implementation owner consults its actual local Playbook. This router does not claim that a phase's scaffold, helper or external example is packaged. Missing material inputs block that dependent phase. A provider-specific recipe that requires another stack is an unavailable method, not a reason to silently change Starter's platform.

## Failure and acceptance

An unrecoverable phase failure leaves the build partial. Return the failing phase, exact command or inspection, actual error, candidate identity, attempts, suspected requirement and smallest owner decision. Keep useful completed artifacts saved; do not improvise a different framework, install tools or change services to make the report green.

Close with Security Review, fixes and affected rechecks, then independent Quality Review against the approved plan. Dependency Review applies to changed packages and provenance. The coordinator directly performs GitHub Workflow's repository-health review of the final candidate. Present the reports to the owner before any authorized commit, push or live release. Report an unexecuted smoke check, missing browser test, unconfigured provider and unavailable plugin as pending.

## Narrower routes

A deploy-only question goes to the existing selected platform owner for preparation within its actual tools. A component adjustment goes to Design Foundation or the relevant narrower UI owner. Existing content edits go to Website Builder or Project Notebook according to the artifact. A broad website build is not a request to create accounts, install dependencies, operate production or choose marketing strategy.
