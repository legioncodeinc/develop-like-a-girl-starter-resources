# Workers as the application backend

Use the existing framework scaffold and pinned versions. Cloudflare's framework guide shows C3 producing a Worker entry and framework/Vite configuration; tooling evolves, so do not invent an equivalent command or migrate an existing CLI. When later provisioning is authorized, use current official instructions for that scaffold and the owner's target environment. The installed Playbook itself has no shell tool and cannot automatically install or deploy.

Every request receives env bindings and execution context. Pass these into server services explicitly. Never store a request, mutable user client, user identity, cookie collection or personal result at module scope. A module-scope request handler factory may be reused when it carries no user state. Avoid Node-only filesystem/process assumptions; Workers expose Web APIs, and nodejs_compat supports selected Node APIs with a specific compatibility date and package constraints. Preserve existing flags; do not claim a flag makes every Node dependency compatible.

Secrets are server-only bindings. Local development secret files must be ignored by Git and must not be read back into chat or included in generated examples. Use names or placeholders in documentation. VITE_ variables and browser bundles are public. Verify bindings by names and types, not by printing values. Build output or source maps can still leak secrets if server modules enter the client graph.

Use Workers Static Assets for built public assets through the framework integration. Let the scaffold set the client build directory. Do not add a catch-all SPA HTML fallback to an SSR application; that can conceal missing routes and bypass request logic. Requests requiring authorization must reach server code before protected bytes are returned. Keep personalized HTML, redirects and auth refresh responses private/no-store. Serve only intentionally public assets from the public build directory.

Treat Supabase, Resend and R2 as distinct server integrations. A browser request cannot choose a privileged account or arbitrary upstream URL. Validate payload size, identifiers and authorization before using a binding. Use timeouts and safe failure responses where the chosen API supports them. Unfinished work cannot be made durable merely with ctx.waitUntil; background-job provider selection is still unresolved. Do not choose Queues, Workflows or a scheduler as an incidental dependency.

A real check should distinguish local emulation, remote provider use and production. Keep remote binding flags off by default. Before any authorized runtime test inspect its configuration so a local command does not silently use remote resources. A successful local build proves bundling only; a local Worker response proves that path under emulation only. Deployment and live provider proof remain separate evidence.
