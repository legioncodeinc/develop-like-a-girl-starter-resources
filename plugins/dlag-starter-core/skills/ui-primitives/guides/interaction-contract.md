# Interaction contract

For each control record purpose, accessible name, native element, states, focus behavior and result. Keep labels visible wherever possible. An icon beside text is decorative; hide its SVG from assistive technology. An icon-only button needs its own accessible name. Use a few explicit named icon imports or a small allowlisted map. Never import an entire icon namespace just to look up arbitrary user strings.

A modal dialog needs a meaningful title, modal semantics, initial focus inside, Tab/Shift+Tab containment, a visible close or cancel action, Escape behavior and focus returned to its trigger or a logical successor if the trigger disappears. Background interaction must be inert and page scroll controlled by the installed primitive. `aria-modal` alone does not trap focus or block interaction. Preserve the primitive's implementation and verify actual behavior; do not add blanket body positioning fixes. Ordinary confirmation cancellation and Escape must never perform the destructive action. Destructive or urgent confirmation uses the installed alert-dialog pattern with clear consequence text and safe initial focus. Never trap the user in a mandatory confirmation without an exit.

Use inline validation next to its field, linked with `aria-describedby` and `aria-invalid` where appropriate. Keep important errors visible until resolved. A quiet result can use an existing polite live region (`role="status"`); urgent asynchronous failures may use a deliberately assertive alert. Do not announce every render or move focus to a toast. A transient toast cannot be the only record of an important failure. Keep undo actions keyboard reachable and duration adequate. Reuse the existing toaster if present; do not add a second notification system.

SSR theme decisions must agree between server HTML and first client render. For an existing cookie-based explicit preference, validate light/dark/system on the server and pass the same initial value to the document and UI. A theme cookie is preference data, never an auth decision. For a simple system theme use CSS `prefers-color-scheme` without browser reads. For explicit classes use the existing selector plus Tailwind v4 `@custom-variant dark` only if that strategy is already configured. Read browser-only state in event handlers/effects after hydration, never at module evaluation or during a server render. A `typeof window` branch that changes initial markup still risks a mismatch. Do not silence mismatches with blanket hydration warnings. Avoid an inline pre-paint script unless the project explicitly needs one and its CSP/nonce arrangement is addressed.

In one browser batch, check keyboard opening, focus order, Escape/cancel, focus return, background isolation, long content, small viewport, pending/errors, theme reload and hydration console. If browser tools are unavailable, record these as unrun and provide exact expected behavior. Do not claim a WCAG audit from this checklist.
