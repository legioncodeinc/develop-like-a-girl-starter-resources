# Application Search procedure

1. Inspect what users need to find and the existing schema. Start with database-backed title/text search, not an embedding service. Use the [search contract](../templates/search-contract.md). Choose exact, prefix or full-text behavior deliberately; document language, punctuation and empty-query behavior.
2. Authenticate before searching. Apply the verified owner filter/RLS before search, count and pagination. Search snippets, suggestions, autocomplete, exports and error messages obey the same boundary. Never fetch all owners' records and filter them in React.
3. Use the [query parser](../examples/search-input.mjs) to bound query length and page size. Choose fields and ordering from fixed code; use Supabase query values or bound RPC arguments, never user-built SQL fragments or `.or()` filter syntax. Empty search returns the permitted bounded list or an explicit empty state.
4. For full-text search, use a maintained generated tsvector/index and a reviewed database function only if needed. Bind the search string with `websearch_to_tsquery` or the SDK equivalent, use security-invoker semantics, restrict table/function grants, retain the owner predicate and return only approved fields. Ask `dlag-starter-core:data-foundation` for schema/RLS and migration boundaries. A recipe is not an applied migration.
5. Render a labelled search input, submit/clear action, result count and empty/error state. Keep the query in the URL, reset pagination when it changes and escape snippets as text. Debounced suggestions must cancel/ignore older responses and still enforce limits server-side.
6. Check owner A versus owner B, blank/long/punctuation queries, no results, stable next-page behavior and failed requests. Save the contract and exact results; production index/query timing remains pending without observed database evidence.
