# Application Onboarding procedure

1. Identify the user's first useful action and the smallest checklist that leads there. Use the [activation checklist](../templates/activation-checklist.md), normally two or three steps. Start with inline guidance, not a purchased tour service or a blocking overlay. Do not introduce a coach, analytics service or mail sequence.
2. Derive completed work from server-owned records where possible. Authenticate every progress read/write and scope by user; validate versioned checklist step IDs. A client checkbox alone cannot prove a required account action occurred. Persist an explicit dismissal separately from completion. For a demo, label mock or local-only progress clearly.
3. Explain each step in plain language with a visible link/button to its action. The flow works with keyboard and screen reader, supports skip/dismiss and return, and never hides required navigation. Preserve focus and do not open repeated dialogs after every navigation. If a tooltip tour is expressly needed, register stable `data-tour` anchors, include escape/focus return and check mobile layouts through `dlag-starter-core:ui-primitives`.
4. Use the [progress model](../examples/progress.mjs) to calculate a count from server-authorized completed IDs. Display text such as 1 of 3 complete alongside any progress bar. Do not call a user fully configured because they viewed a page.
5. Check a new user, returning user, dismissed flow, invalid step, another user's progress and keyboard navigation. Save the completed checklist and actual evidence. An unrun scenario stays pending; use `dlag-starter-core:ready-check` for readiness statements.
